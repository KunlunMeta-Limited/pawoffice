# 通用 Multi-Agent 前端建议与当前实现对照

2026-10-28。依据用户提供的 ChatGPT 参考文本、当前分支代码和浏览器回归。这里讨论产品能力与交互，不替换 PawOffice 的办公室场景、现有服务和通信架构。标为“已实现”仅指对应能力，不能理解为整个模块没有待改进项。

## 总体判断

当前已有会话、消息、成员任务、成果和人工确认的基础；本次也已加入历史交付和固定版本预览。主要缺口不是再增加更多展示卡片，而是**用户需求、Agent 执行、交付成果之间缺少可追踪的关联**。因此用户能分别找到聊天、任务、文件，却很难回答“这句话触发了哪些执行，为什么失败，交付了哪几个版本”。

参考中的三栏布局是可选表现方式，不是能力验收要求。保留办公室主界面，聊天中放轻量结果入口，沿用当前成果阅读器和后续执行详情抽屉即可；无需先重做整个页面。

## 实现得还不够好的地方

### 1. 多处“文件/文档”数据没有统一身份

`result.artifacts` 已有真实内容、版本与预览能力；`sections.documents` 只有名称、版本文字、日期、状态；`sections.files` 主要是附件 URL。当前 `resultDeliveryLayout()` 按唯一标题匹配去重，只能算兼容处理。

标题可能重名、改名或语言变化，不能作为长期关联键。应让文档、附件、图片等展示项引用稳定 `artifactId`，必要时加 `versionId`，统一进入预览器。避免看起来像文件却不能打开、同一文件出现两次或更新后失去关联。

验收：两个同名文件也能独立打开；重命名不会丢历史；历史入口不会打开当前工作文件。

### 2. “过程记录”还不是执行诊断界面

任务步骤最多 3 项，更适合阶段摘要。它不能承载十几个 Agent、并行工具调用、多次重试。检查时还发现未填写 `step.state` 时，失败/受阻任务的首个未完成步骤可能被推导为 active；本次已限制为仅 running 时推导，历史记录没提供任务状态时也不再声称已完成。

应保留阶段摘要，另提供按真实执行记录渲染的时间线：Agent、动作摘要、状态、时间、错误；点击展开工具调用。缺依赖关系时只表达时间顺序和实际父子归属，不把事件顺序画成 DAG。

验收：并行 Agent 可以同时运行；失败项保持失败；重试是独立尝试；工具详情不是聊天回复全文。

### 3. 历史可查看，但不容易查找

当前用下拉框选交付，适合少量轮次。没有“新增 1、更新 1、沿用 1”的交付差异摘要，没有按产物搜索，也无法从用户消息直达这次交付。外部历史 JSON 按需加载后，仅知道已加载记录和内联记录里的版本，不保证下拉框列出后端全部历史版本。

近期先增加聊天交付入口和明确的交付名称/时间；轮次较多时再做可搜索历史列表、后端分页与独立版本目录。不能用浏览器扫描工作区补齐历史。

### 4. 版本预览还不是完整 ArtifactViewer

已有固定版本机制，但当前是成果弹窗再打开预览弹窗。临时查看合理，频繁在多个文件间切换就显得层级较深。桌面端可演进为阅读器内可伸缩的预览区域或并列面板，手机保持单页预览；仍沿用现有办公室入口。

补 PDF、CSV、代码高亮、JSON 结构化查看；统一加载/失败/不支持/过大/无权限的提示与恢复操作。签名地址过期后需要业务后端提供刷新机制，当前没有自动续签。

### 5. 展示类型偏向研发交付，应该收敛主入口

接口表、部署环境、测试面板等只能是后端确实提供对应数据时出现的可选区块，不应作为所有 Agent 任务的默认模板。用户真正需要的是结论、真实产物、可信验证、异常和下一步。

建议把真实文件统一到 artifacts；`changes` 表达代码变更；结构化表格/图表用于结果正文；其余业务预设保留兼容。后端传数据，不传 React 组件、CSS 或任意可执行页面。

### 6. 视觉统一与可读性还需打磨

当前已减少堆叠、采用概览/交付物/过程记录分层。仍有重复的状态胶囊和颜色常量、偏小的辅助字体，以及多个“版本记录/交付轮次/文档版本”概念。检查时发现当前累计成果仍写“本轮结论”，本次已区分为“成果概览”和历史“本次交付”。

建议统一设计令牌、文件图标、时间格式和状态用语；当前集合写“成果概览”，历史写“本次交付”；默认只显示一个主要状态及最重要异常。不要通过增加更多卡片解决信息层级问题。

### 7. 文档和样例需要跟随真实行为

旧说明仍描述“白板/成果”切换和四个旧标签，容易误导接入方；本次已修正文档入口并增加独立的交付协议说明。早期截图属于历史版本，不应作为当前界面验收依据。

样例覆盖三轮：范围确认、首次文档、更新旧文档并新增报告；真实业务后端仍需提供版本存储和访问权限。PawOffice 缓存快照不等于服务重启后永久保存历史。

## 建议实施顺序

| 优先级 | 工作 | 对用户的直接收益 |
| --- | --- | --- |
| P0 | 接入方落实不可变版本 URL、交付目录和校验对象；完成三轮真实联调 | 历史版本可信，成果状态不会混淆 |
| P0 | 补消息与执行/交付的明确关联，聊天中出现轻量交付入口 | 不再需要猜测成果放在哪里 |
| P0 | 执行时间线最小版及工具调用详情，展示失败/等待/取消与错误 | 看得懂谁在做什么、哪里卡住 |
| P1 | 统一 artifact 身份及预览入口，补 PDF、代码、CSV、JSON | 文件真能打开，减少重复与纯展示卡片 |
| P1 | 历史列表搜索/分页、完整版本目录及任意两版对比 | 多轮使用后仍可查找和审阅 |
| P1 | 预览空间、字体、文案、设计令牌统一 | 减少多层弹窗和视觉碎片 |
| P2 | 跨会话成果搜索、Run 筛选/统计、真实依赖图 | 规模化管理；需要后端对应数据 |

这里的 P0/P1 是下一步的建议，不代表上述扩展已在本次全部实施。应先约定关联数据，再做交互；不改变现有项目运行架构，也不新增 Agent 编排职责。
