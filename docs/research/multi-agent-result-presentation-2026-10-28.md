# 多 Agent 系统的结果展示调研

调研日期：2026-10-28。

目标：为 PawOffice 的成果界面、后端输出契约和多 Agent 协作追溯提供依据。本次查阅官方文档、官方产品更新及官方开源仓库；没有登录付费控制台或运行全部竞品。开发调试界面、面向使用者的交付界面、通信协议分别比较，不能视为同一种产品。

## 1. 六类界面的实际做法

| 对象与定位 | 官方资料能够确认的做法 | 对 PawOffice 的启发 |
| --- | --- | --- |
| [AutoGen Studio](https://microsoft.github.io/autogen/dev/user-guide/autogenstudio-user-guide/usage.html)：多 Agent 原型与调试 | Playground 可查看生成的文本、代码、图片，以及 Agent 消息、工具动作和执行统计 | 产物与协作过程都应可访问；调试信息的密度要根据使用者身份控制 |
| [CrewAI AMP Traces](https://docs-platform.crewai.com/platform/en/features/traces)：运行观测 | 同一次执行提供摘要、Tasks & Agents、Final Output、时间线与任务详情；任务详情包括输入、输出和执行状态 | 总成果可以汇总，但要能回到贡献该成果的具体任务与 Agent |
| [LangSmith Studio](https://docs.langchain.com/langsmith/studio)：Agent IDE | Graph mode 展示节点与中间状态；Chat mode 提供更简单的对话体验 | 业务阅读与开发排错可以共用数据，但应提供不同的信息密度 |
| [Deep Agents 前端模式](https://docs.langchain.com/oss/python/deepagents/frontend/overview)：协调者与子 Agent 界面 | 协调者消息、子 Agent 状态、计划及工具调用分别暴露；官方给出可折叠子 Agent 卡、任务列表、文件浏览与 diff 面板等模式 | 保留汇总结论，同时让用户知道哪些子任务在执行、哪一步需要干预 |
| [OpenHands Agent Canvas](https://www.openhands.dev/product/canvas)：并行编码 Agent 工作台 | 支持多个 Agent/工作树；[官方更新](https://hub.openhands.dev/blog/new-in-agent-canvas-august-2026)说明了对话中的 Markdown 预览、文件入口、Git 状态和提交检查抽屉 | 编码成果的重要对象是可检查的文件与改动；结果说明应能定位到工作区中的产物 |
| [Google ADK](https://adk.dev/artifacts/)：多 Agent 运行与产物服务 | Artifact 按文件名、版本与 MIME 类型管理，可保存、列出和读取；[Web UI](https://adk.dev/runtime/web-interface/)还提供聊天及事件/执行轨迹相关视图 | 产物应有稳定身份和内容类型，避免把所有内容都内联进一份展示 JSON |

LangChain 的 [Agent Chat UI 官方仓库](https://github.com/langchain-ai/agent-chat-ui#rendering-artifacts)还提供了一种明确的阅读布局：聊天中的入口打开右侧 Artifact 面板。这是可采用的交互模式，不代表所有 LangGraph 应用都默认如此。

## 2. 两个协议层面的发现

### A2A：执行、消息与产物是不同对象

[A2A Core Concepts](https://a2a-protocol.org/latest/topics/key-concepts/)分别定义 Task、Message、Artifact；内容可以是文本、文件引用或结构化数据。它为结果归属提供了参考，但不规定页面必须画成哪种卡片，也不自动提供“测试已通过”的业务语义。

[任务生命周期说明](https://a2a-protocol.org/latest/topics/life-of-a-task/)还讨论了后续修改与产物版本的关联：重新生成的结果需要能联系到之前的任务和产物。对 PawOffice 的建议是保留每轮执行的身份和历史，而不是不断覆盖一个不带执行标识的当前成果对象。

### A2UI：下发声明式组件是一条成立的路线

[A2UI](https://a2ui.org/)允许 Agent 下发声明式 UI，由客户端使用组件目录进行原生渲染；[组件说明](https://a2ui.org/concepts/components/)包括组件 ID、数据绑定、增量更新和自定义目录。

因此，“后端描述组件一定不合理”是不准确的。需要区分两类需求：

- **交付阅读**：给用户答案、文件、改动及验证依据。通常优先采用稳定的产物和状态数据。
- **动态交互**：Agent 根据任务生成选项、表单、可操作图表等界面。此时声明式组件协议有明确用途，也需要完整的操作回传机制。

PawOffice 目前最迫切的成果阅读需求，不足以成为全面引入动态 UI 协议的理由。现有通用内容块可以保留为扩展能力，避免要求每个后端按固定业务卡片目录拼整页。

## 3. 从这组样本得出的设计判断

以下为本次对照后对 PawOffice 的建议，不是各竞品共同实现或统一标准。

1. **结果与过程分别组织，并建立关联。** 首先让用户看到结论和产物；检查问题时，再进入相关 Agent、任务、工具输出与日志。不能只交付一串 Agent 消息，也不应让用户遍历整条日志才能找到文件。
2. **产物需要身份、内容和来源。** 除标题外，逐步补足产物 ID、内容类型、访问地址或正文、生成该产物的任务/执行/Agent，以及必要的版本信息。
3. **执行结束与验证通过分开表达。** “运行完成”描述执行状态；“测试通过”“用户已验收”需要各自的检查或操作依据。模型的总结文本不应直接成为已验证状态的唯一来源。
4. **按内容类型提供阅读器。** 文档、图片、代码差异、表格文件可以有不同阅读方式；没有阅读器的文件仍应有可用的访问或下载入口。业务名称不需要逐一对应新的专用组件。
5. **运行中也要有可理解的输出。** 显示已完成的子任务、正在执行的动作、已产生的部分产物，以及明确的阻塞原因或待输入事项。页面不能只剩一个无上下文的进度百分比。
6. **多 Agent 的价值体现在协作归属。** 需要能回答谁产生了文件、谁修改过、谁做了验证，以及失败发生在哪个环节。仅增加 Agent 头像和多列卡片不能回答这些问题。

## 4. 对当前 PawOffice 的具体评估

| 当前能力 | 判断 | 建议 |
| --- | --- | --- |
| 概览 / 交付物 / 过程记录 | 已有阅读分层基础 | 保留，重点增强内容之间的定位与关联 |
| Markdown 交付物和图片 | 已有基本阅读能力 | 将实际产物作为主要入口；继续补充真实文件访问与预览 |
| 文件变更清单、增删行数、逐行 diff | 直接服务编码任务 | 保留；后续绑定执行轮次和比较基线，大补丁按需读取 |
| 白板任务状态与成果状态分开 | 方向合适 | 进一步让验收状态对应真实证据，避免仅凭总结判断 |
| `gallery/api/environments/documents/...` 专用区块 | 能表达一些特定业务，但容易被当作必填模板 | 按需求使用；不把接口清单等内容作为每份成果的默认章节 |
| `custom` 与通用内容块 | 有扩展用途 | 保持可选，不让一般任务接入承担整页布局编排 |
| 成果挂在 `whiteboard.result` | 适合当前会话的一份成果，缺少独立执行历史 | 后续引入执行标识与产物归属，先建立关联，不立即改成多个复杂页面 |
| `versions[]` | 当前是版本说明列表 | 不将其当作实际内容快照；需要后端保存可读取的产物版本 |
| 多 Agent 的任务贡献关系 | 当前有成员、任务和成果，关联仍不充分 | 增加成果来源、贡献任务与验证执行者，允许从产物进入相关过程 |

## 5. 建议的成果阅读方式

默认阅读内容围绕这四项组织：

1. 一段汇总结论：交付了什么、是否可用、还有什么限制。
2. 可打开的产物：文件、文档、图片或运行结果。
3. 实际改动和验证摘要：存在代码改动时显示 diff；存在测试或审核时显示证据与状态。
4. 相关协作入口：点击才展开贡献该结果的 Agent、任务和过程记录。

可考虑让聊天中的交付条目打开成果侧面板，以便用户边看结果边继续交流；现有工具栏入口和白板入口可以指向同一产物与同一阅读器。侧面板是否优于当前模态框，应结合主页面可用宽度验证，不应只因竞品采用而直接替换。

### 后端数据的职责边界

建议逐步收敛到以下几类事实对象；这是未来演进方向，不是本轮新增的已发布协议字段：

| 对象 | 负责表达什么 |
| --- | --- |
| 一次执行 | 做什么、执行状态、起止时间、所属会话、父子执行关系 |
| 产物 | 是什么、如何读取、由谁在哪次任务中产生、所属版本 |
| 文件改动 | 比较基线、路径、变更类型、统计、补丁或读取补丁的引用 |
| 验证记录 | 检查对象、结果、证据、验证者、时间 |
| 过程事件 | Agent 开始/结束、工具执行、阶段进展、错误与恢复 |
| 用户待办 | 缺少的输入、需要确认的动作，以及操作结果 |

前端根据这些对象决定显示状态、正文、文件卡、差异阅读器和相关过程。已有 `office.snapshot` 和运行命令无需因这项调研改变；后续协议演进应逐项兼容，而不是一次替换整套接入。

## 6. 优先级

- **P0：让当前成果可用。** 清楚的结论、真实文件访问、可靠 diff、明确验证依据，移除重复无效的样例区块。
- **P1：让多 Agent 的贡献可追溯。** 执行标识、产物与任务/Agent 的关联、相关过程定位、跨轮查看。
- **P2：扩展阅读与运行体验。** 按需读取文件/大补丁、持久化产物版本，以及需要时才引入表单等动态 UI。

仓库已有的 [DSH 文件改动调研](./dsh-result-changes.md)区分了改动记录与主动展示的交付文件；本次将其作为既有笔记参考，没有重新核验其中对应版本的本地源码。
