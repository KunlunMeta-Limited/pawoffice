# 成果展示模块：当前缺陷与补足清单

日期：2026-10-29。依据用户提供的 Claude 分析、当前 `feat/result-reader` 分支代码以及此前的验证记录。本次为静态梳理，没有重新执行浏览器验收，也没有修改业务代码。

## 1. 总体判断和范围

成果模块已经能展示内容、文件变更和固定历史版本。接下来需要把它做成用户能够可靠找到文件、理解每次交付的变化、判断成果是否可用的业务界面。

本清单只讨论成果入口、成果概览、交付物、预览、版本、验证、错误恢复，以及与成果有关的过程追溯。完整 Agent 编排、任务取消/重试系统、DAG、数据库和文件版本仓库不属于这一轮成果页面的前端工作。

已有能力应继续利用：正式办公室“当前成果”入口；概览/交付物/过程记录；文件变更清单与逐行 diff；当前成果与历史交付分开；固定版本预览、下载和与当前文本比较；检查版本失效提示；加载和部分错误状态。不能把这些重新列成尚未开发。

## 2. P0：先补正确性和基本可用性

### 01. 成果入口仍受白板条件影响，聊天入口未验收完成

现状：聊天回复下已有交付入口，跨会话打开失败的浏览器用例还未通过。当前白板读取逻辑要求标题非空；没有标题时，即使存在有效交付数据，也可能无法取得成果入口所依赖的白板对象。会话切换时是否还有同步竞争尚未验证。

用户影响：已经看到了交付条，却打不开；标题这样一个展示字段可能阻断真实成果访问。

补足：成果读取不应以白板是否有可显示标题作为必要条件；同一成果阅读器应能从工具栏或聊天直接打开。缺标题可以显示兜底标题，真正缺交付/权限/同步失败则显示对应原因。按办公室、会话、交付 ID 定位，并验证 `{有标题/无标题} × {首个会话/其他会话}`。

验收：所有组合均可正确打开；来回切换不串会话；刷新后仍能打开指定历史；无此交付时不回退展示另一轮内容。

### 02. 同一份文件的身份与打开方式没有统一

现状：`artifacts` 有内容和真实版本；“文档清单”主要是标题、版本文字、日期和状态；“附件”主要是 URL。部分文档去重按唯一标题匹配，而不是按稳定文件身份。图片/附件等也没有全部走同一版本预览入口。

用户影响：同名文件难以区分；改名后可能重复；有些看起来像交付文件的条目不能打开，另一些直接跳外链。

补足：真实可读取产物统一使用稳定 `artifactId` 和需要时的 `versionId`。不同列表是同一文件的不同表现，不再各自维护一份互不关联的数据；纯说明文字不伪装为可打开的文件。

验收：两个同名文件独立打开；改名保留身份和历史；同一版本从任何入口打开都得到同一内容。

### 03. “下载”的含义不一致，容易拿到不同内容

代码可确认：预览弹窗中的“下载该版本”使用读取并在有哈希时校验过的原始字节；但文件卡片的“下载”仍会将内联内容加上标题，导出为 `.md`，没有统一的版本文件名。这两种行为并不等价。外层 JSON 导出的是完整白板数据，也不是自动随历史选择变成单次交付导出。

用户影响：查看的是某份文件，下载得到的却可能是加工后的 Markdown；查看某次历史时，也难以判断导出的是哪一层范围。

补足：明确区分“下载该版本原文件”“导出成果报告”“导出原始数据”；真实文件下载复用版本读取逻辑，保留正确 MIME、扩展名和版本。当前汇总与历史交付的导出范围要在操作前明确。

验收：同一版本的各个原文件下载入口内容一致；JSON、代码和图片不会统一变成 Markdown；导出本次交付不会混入其他轮次内容。

### 04. 总状态与当前版本验证可能相互矛盾

现状：检查绑定旧版本后，页面能显示“需重新验证”；但是头部成果状态仍直接按后端 `result.status` 展示。如果后端仍传 `verified`，可能同时出现“成果已验证”和“当前版本需重新验证”。未绑定版本的旧检查也不能判断是否适用于当前产物。

补足：与后端约定整体状态和检查对象的一致性；前端发现冲突时明确指出“后端标记已验证，但当前检查已失效/存在未通过项”，而不是只显示一个成功标签。检查应尽量说明对象、版本、时间、验证者和证据入口。

验收：更新 v1 为 v2 后不沿用 v1 的通过结论；未提供验证时明确显示；不能仅因执行完成或所有已列检查通过，就擅自生成整体验收通过状态。

## 3. P1：补足多轮阅读、预览与判断信息

### 05. 当前汇总、本次交付、文件版本的范围仍不够清楚

已有历史选择和提示，但阅读器外层始终叫“当前成果”；界面同时还有“版本记录”“文档版本”“交付轮次”等概念。

补足：清晰标识正在看“当前有效成果汇总”还是“某次历史交付”；让用户能回答“这个文件这轮新建、更新，还是沿用”。增加交付变化摘要，例如新增 1、更新 1、移除 1；沿用文件标明来源，是否在该次交付详情中显示由产品规则决定。

明确历史语义：当前实现的单次交付可以仅包含当次新增/修改内容，不能把它称为那一刻完整文件集合。若要“回到当时查看全部有效文件”，后端还需提供该时刻的集合快照，或可还原的明确记录；前端不能猜。

### 06. 当前采用版本与最新创建版本被混称

现状：预览器把当前成果中的版本当作“最新版”。只要与查看版本不同，就提示“已有更新版本”。在后端回滚到较旧版本的情况下，这个提示不一定成立。

补足：至少区分“当前采用版本”和“正在查看版本”；需要展示“最新创建版本”时由后端明确提供。回滚、重新生成、移出当前集合应有可理解的说明。

验收：当前从 v2 回滚采用 v1 时，不向正在看 v2 的用户宣称 v1 是更新版本；历史 v2 仍可查看。

### 07. 文件差异没有明确的比较基线

已有增删行数和 unified diff，但结构中没有明确的比较基线：相对上一轮、上一版、Git HEAD 还是工作树？文件变更项也没有统一关联可打开的产物版本。

补足：后端提供可读的基线说明，必要时带基线/目标标识；界面显示“相对谁的变化”。区分工作区文件变更和主动交付的文件，在有关联数据时允许互相打开。

此外清单最多 24 个文件，目前没有完整文件总数/分页语义。数据被后端裁剪时，不应让局部合计看起来像全部改动；应显示“已列出 N 项/完整范围未提供”，或有真实总数时展示已加载/总数。

### 08. 读取失败虽有提示，但恢复路径不完整

已有 404、格式不符、交付错位和哈希失败等提示，并非完全没有错误处理。但不少权限、超时、跨域或过期地址仍以一般失败呈现；文档预览缺少统一重试入口，历史交付重试则已经有。签名地址续期能力未提供。

补足：区分读取中、不可预览、权限不足、版本不可用、地址可能过期、校验失败、网络失败；根据后端实际能力提供重试、重新获取地址或原文件入口。校验失败时仍停止正文展示，不能自动换版本。未提供哈希时只说明未做内容校验，不能暗示内容已被验证。

### 09. 预览容器和格式覆盖不足

当前是成果弹窗再开文档弹窗。频繁切换文件、返回交付、比较版本和继续聊天时上下文被遮挡。桌面并列面板或单容器内的“交付 → 文件 → 版本/差异”返回导航值得验证，但不是未经布局验证就必须采用的定案。

已有 Markdown、图片、文本；代码/JSON 只是源文本。需按真实任务优先补 PDF、CSV 表格、代码高亮和 JSON 结构查看；音视频、Office 转换可后置，不需要同时引入所有渲染器。

验收：用户可以完成打开文件、切版本、比较、返回原交付、继续聊天，且保留选择和阅读位置；窄屏也可完成；不支持的格式仍有正确版本的访问途径。

### 10. 历史目录和版本列表不能代表完整历史

当前交付目录最多 20 条，当前结果最多 8 个 artifacts；没有目录分页和产物搜索。文档版本选择主要收集内联历史、当前选中且已加载的远程历史和当前成果，不会自动得到远端全部版本。

补足：说明当前加载范围和是否还有更早记录，按需引入交付目录分页及文件版本目录。稳定历史链接最好能通过会话+交付 ID 单独解析，不要求始终把它放在最近 20 条目录中。分页后必须重新明确“未加载”和“已删除”，不能将未加载误判为删除。

### 11. 检查、风险、决策与成果之间缺少定位

“过程记录”现在包含多种性质的信息；用户看到失败检查或风险，还需要自己寻找对应文件。真正的执行时间线和工具详情尚未实现，但不是必须先建完整时间线才可改进成果页。

近期可补：文件打开对应验证，检查跳到所验证的版本，风险说明影响哪个交付物，决策说明影响范围；概览只显示关键结论和待处理项，细节按对象展开。将来的过程追溯只作为相关 Agent/执行入口，不要求用户读完整日志才能找到结果。

### 12. 可选内容区块和真实交付物的主次需要收敛

接口、环境、测试等业务预设与通用内容块并存，容易把接入方引向拼展示页面。纯元数据卡片、占位图和重复清单即使样式统一，仍会造成堆砌。

补足：把总结、真实产物、必要变更、验证与异常作为主线；业务预设和通用块按后端真实数据出现。不要求每次交付都包含指标、接口、环境或图表；没有实际文件时说明这是总结/阶段记录。统一字号、间距、状态文案和操作样式，并移除重复表达。

## 4. 对 Claude 建议的必要修正

1. **“审批未实现”过于笼统。** 项目已有确认、选择、自定义回答、超时和回执。缺的是与具体成果/验证对象绑定的业务验收流程，以及完整执行控制，不应再造一套基础菜单。
2. **“回滚一定新建 versionId”不必作为通用硬规则。** 可以记录一次新的交付/回滚操作，将当前引用改回已有不可变版本；如果确实生成新的版本对象，也应保留回滚来源。关键是历史内容不可覆盖，且操作可追溯。
3. **“无文件就不显示交付”不是唯一选择。** 实际存在的总结、阶段结论也可以作为一条交付/阶段记录。要避免的是假文件、无意义的空卡片；可将“文件交付”与“仅总结”用文案区分。
4. **“每个当前版本都要在已加载历史中找到”要求过强。** 历史可能分页或只保留目录窗口；应保证引用可通过后端解析，并能查看来源，而不是要求全部历史常驻当前快照。
5. **删除和回滚事件值得表达，但不必立刻实现完整事件溯源或强制 tombstone 存储。** 后端明确当前集合与当次变化、前端能展示移除原因和历史即可，再按业务扩展。
6. **seq 恢复不是当前完全未设计的能力。** 已有后端保持版本连续的约定、SSE 重连和服务状态标识处理。真实业务后端是否遵守仍需联调，但不应列为成果页面必须重写的架构缺陷。
7. **一上来引入全部 Run/AgentRun/ToolCall 对象不是成果模块的前置条件。** 当前先完成交付入口、产物身份与版本正确性，再逐步增加来源和验证关联。

## 5. 建议交付顺序与范围

| 阶段 | 要达到的业务结果 | 本轮重点 |
| --- | --- | --- |
| 第一批：可用且可信 | 点得开、不会认错文件、下载与查看一致、验证状态不矛盾 | 01–04 |
| 第二批：多轮清楚可读 | 看懂本次改了什么、相对谁变化、正在看哪个版本 | 05–07，加必要的错误恢复 08 |
| 第三批：阅读效率 | 常见文件好读、返回路径清晰、历史可查找 | 09–10，配合视觉统一 |
| 第四批：成果可追溯 | 文件能关联验证、风险、决策和必要的 Agent 来源 | 11，并按需接真实执行记录 |

以上是缺陷整理与建议范围，不表示这些补足已完成。接下来的验收应覆盖：两份同名文件、文件改名、无白板标题、切换会话、第三轮更新第二轮文件、旧版缺失、地址过期、失败检查、验证过期、回滚采用旧版、历史超过目录窗口，以及文件原件下载一致性。
