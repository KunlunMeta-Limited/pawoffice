# 成果体验优化方案与实施说明

日期：2026-10-28。范围：当前分支的成果阅读、白板详情、正式页面入口及状态展示。

后续实施已将“本轮成果”入口更名为“当前成果”，增加按次历史与固定文件版本。当前集合、历史交付、版本预览和外部存储分工以 [交付协议补充](result-deliveries.md) 为准；下文保留早期方案背景。

## 1. 产品定位

成果是当前会话围绕一个目标形成的交付，不等同于某个员工的一条子任务。现有数据挂在 `whiteboard.result`，没有任务级成果关联。本轮以“本轮成果”命名入口，沿用当前会话的数据作用域。

用户进入详情后，应能按顺序回答：

1. 这轮要完成什么，现在交付到什么程度？
2. 成果能否使用，有哪些问题需要处理？
3. 在哪里查看、复制或下载交付内容？
4. 需要追溯时，如何找到任务、验收、决策和版本记录？

保留现有结构化渲染能力，调整信息顺序与交互。无需为了本轮视觉修改引入新的布局协议。

## 2. 入口与原页面集成

### 已实施

- 在场景公共工具栏增加“本轮成果 + 状态”按钮；经典布局和成员布局共用。
- 入口不依赖成果已经完成，也不依赖场景的互动动画加载完毕；有任务白板数据即可查看。
- 点击场景白板或工具栏入口，打开同一个 `WhiteboardReader`。
- 优先读取当前 dashboard 的白板数据；没有墙上白板物件时，仍支持通过公共入口读取会话白板。
- 切换会话时关闭上一会话的详情；详情状态按会话重新初始化。
- 桌面复用模态详情，手机使用全屏详情；支持 Escape、关闭按钮和关闭后的焦点恢复。

### 为什么选择此位置

经典布局已有窄任务侧栏，成员布局没有对应的右侧任务栏。公共场景工具栏是两者都具备的位置，可以先建立稳定入口，避免复制两套页面。详情保留在办公室上下文中，用户关闭后可以继续对话。

### 后续建议

- 聊天中增加真实的交付事件卡片，引用同一份成果并打开同一容器。
- 任务列表只有在存在明确的 `taskId → resultId` 关联后，才显示“该任务的成果”。
- 如果用户需要同时对照场景与成果，可进一步将详情改为可调整宽度的侧面板；不要把完整成果内容压进现有约 292px 的任务侧栏。

## 3. 信息架构

合并“任务白板 / 成果 / 任务详情”三套视图，固定保留一层导航：

| 区域 | 内容 | 交互原则 |
| --- | --- | --- |
| 公共头部 | 当前目标、任务状态、成果状态、负责人、团队、更新时间 | 任意标签下都能识别目标与状态 |
| 概览 | 状态说明、简短结论、验证结论、主要操作、待处理摘要、关键指标、下一步、阶段进度 | 先给结论；未通过项和未关闭风险不能只藏在历史中 |
| 交付物 | 原有 artifacts、结构化 sections、真实预览及文件链接 | 复用已有内容；缺少内容时明确说明，不画假交付物 |
| 过程记录 | 全部待处理项、验收清单、过程决策、风险、任务明细、版本记录、原白板详情 | 按组展开；版本默认折叠；保留原有详情可读性 |

三个标签始终存在。空数据用明确的空态说明，避免数据更新导致导航消失或重新排序。

有交付物时，概览直接展示前三个文件，支持查看、复制和下载，并通过“查看全部”进入完整交付物标签；仅有结构化章节时展示章节索引。没有交付物时使用“查看执行记录”。复制摘要与下载报告作为次要操作。没有后端能力时不显示“通过验收”“重新生成”“上传文件”等动作。

实时更新只更新数据，不自动将读者从正在查看的页面切换到其他标签。

## 4. 状态设计

### 两条状态线

- 任务状态来自 `board.status`，描述执行过程。
- 成果状态来自 `result.status`，描述交付及验证情况。

“任务已完成 + 成果未通过”和“任务执行中 + 已交付阶段成果”都允许出现。不能用 100% 进度、测试通过率、任务完成状态推导成果已验证。

| 数据情形 | 成果状态展示 | 说明 |
| --- | --- | --- |
| 无成果、queued | 暂无成果 | 尚未开始，之后会在此汇总 |
| 无成果、running | 正在产出 | 等待实际成果内容 |
| 无成果、blocked | 产出受阻 | 引导查看执行记录 |
| 无成果、failed | 尚无成果 | 同时明确显示任务执行失败 |
| 无成果、completed | 尚未交付 | 执行结束不代表收到交付内容 |
| 有成果、draft | 草稿 | 阶段内容可能继续更新 |
| ready | 已交付 | 尚未标记验证通过 |
| verified | 已验证 | 可以查看交付内容与验证依据 |
| rejected | 未通过 | 优先查看验证结论和待处理项 |

本轮保留现有 `ready` / `verified` 的协议含义，不新增审批状态。`ready` 不等于正在等待某个人审批；`verified` 也不凭空代表某位用户已批准。

没有内容时，显式的 ready / verified / rejected 仍然展示其状态，交付物区域同时显示内容缺失。失败后已有的阶段成果继续可读。

### 待处理事项

合并顶层验收清单、结构化测试区块的检查项、未关闭风险及受阻任务。未通过检查和高风险优先显示。概览最多显示三条，并可进入过程记录查看全部；已通过检查与已关闭风险不计入待处理。

待处理项和总体成果状态独立展示，不在前端擅自改写后端状态。

### 后续建议

真正支持验收操作前，应补充验证人、验证时间、验证依据、可执行动作和操作反馈。复用现有决策机制，不能仅添加按钮就让界面看起来具备审批能力。

网络加载、同步失败、数据过期属于数据读取状态，后续应通过 session 的连接状态与更新时间独立呈现，不能把断网直接显示成“成果失败”。

## 5. 视觉规范与内容密度

### 已实施

- 使用项目现有的白色内容面、灰绿中性色和绿色主要操作，减少渐变与装饰。
- 统一详情容器为桌面最大约 960px、16px 圆角；阅读区使用 24/28px 级别留白。
- 目标标题约 19px，结论约 20px，正文 13–14px，元数据 11–12px。手机适当缩小标题，保留正常阅读空间。
- 普通区块改为章节与分隔线，减少“容器里嵌卡片、卡片里再嵌卡片”。关键指标、文件项和需关注区域保留有意义的边界。
- 状态使用“文字 + 语义颜色”，不只依靠红绿区分。
- 头部时间来自后端 `result.updatedAt`，没有时使用 `producedAt`；浏览器按查看者本地时区显示 `YYYY-MM-DD HH:mm:ss`。原始含时区时间戳保留在数据与导出中；未提供业务时间时不以浏览器当前时间代替。旧数据未携带时区时保留其原有钟面时间。
- 页面预览缺失时显示紧凑的“暂无预览”行；有真实图片才显示缩略图并支持打开原图。
- 移除本来只是 caption 的“查看全部 → / 上传文件 →”假操作。
- 文件的“查看”作为主要操作，复制与下载弱化为文字操作。标签支持方向键、Home/End；手机保留同样的三个标签，不增加第二层导航。

### 第二轮视觉优化

- 压缩头部层级：图标、目标标题与元数据组成一个紧凑区域，任务状态放入元数据行，成果状态固定在右侧。
- 桌面概览采用主次两栏：左侧依次阅读结论、关注提示、实际交付内容和下一步；右侧以浅灰绿色背景承载指标与阶段进度。手机回到单列。
- 待处理事项改为轻量提示条，显示数量及优先级最高的一项，通过“查看”进入完整过程记录。
- 概览直接提供文件查看操作，交付物标签在桌面使用双列文件卡，减少长列表的重复滚动。
- 同名文档只有在 artifact 与 documents 清单两侧均唯一匹配时才合并展示；版本、日期和状态附在文件项下。有歧义的条目继续保留，原始数据及导出内容不变。
- 减少嵌套边框与指标卡片，统一操作按钮、图标尺寸和章节间距。

### 内容提供建议

后端应优先提供一至两句 summary，直接说明交付范围和限制。verdict 描述验证结论。metrics 只提供与本次结果判断有关的数据；不为了填满版面固定输出六个指标。

gallery 缺图不应使用看似已完成的线框冒充预览。documents 没有内容或 URL 时只是清单；要提供打开操作，建议先关联现有 artifacts，再考虑扩展协议，避免维护两份互相不一致的文档元数据。

custom blocks 保持为内容扩展能力。是否显示首屏摘要、风险提示和主要操作由前端统一负责，不由任意区块排列决定。

联调样例应模拟真实交付，不作为组件目录：本轮做了什么、产生了哪些文件、代码如何改变、验证依据是什么。接口说明应作为具有请求/响应与错误处理内容的文档交付；不额外堆放只有路径和“已完成”标签的接口清单。样例已移除这类重复区块。已有业务类型的渲染能力不意味着每个后端都需要填充这些类型；展示优先级由前端根据实际产物组织。

## 6. 技术结构与兼容

| 文件/组件 | 职责 |
| --- | --- |
| `results/presentation.ts` | 任务与成果状态映射、待处理项汇总、文档展示合并 |
| `ResultWorkspace` | 唯一的阅读布局、三个标签、概览与过程组织 |
| `ResultReader` | 复用旧指标、交付物、验收、决策与导出能力；按区域嵌入 |
| `WhiteboardReader` | 模态生命周期、完整白板 JSON 下载、焦点恢复 |
| `OfficeSceneControls` | 两种正式布局的公共入口及简短状态 |
| `useOfficeSceneController` | 获取当前会话数据，协调白板与工具栏入口 |
| 电商工作流 mock | 通过正式办公室联调，支持全景与逐轮模式 |

`resultHasContent` 覆盖 sections / tasks / versions / risks / next / note，避免新结构成果被误判为空；墙上白板的成果提示同步补齐。

`OfficeCanvas` 按需加载阅读器，避免访问办公室首页就加载完整成果界面。此次生产构建的首页主 chunk 从接入后的约 504 kB 降至约 281 kB（压缩前；不代表整个应用的总下载量）。

白板详情按“detailSections → 旧 detail Markdown → 简版白板”回退。旧 Markdown 保持 HTML 禁用和安全链接处理，不要求已有接入方立即迁移数据。

预览旧 URL 的 `view=board` 映射过程记录，`view=detail` 映射交付物；默认进入概览。新的参数使用 overview / deliverables / process。

## 7. 验证与验收标准

- 经典布局和成员布局均能从正式入口打开成果。
- 只有 sections、tasks、versions 或 risks 的数据也能在正式阅读器中查看。
- 没有成果时能区分执行中、受阻、失败及完成但未交付。
- 切换成果状态立即更新状态说明，保持当前阅读标签。
- 全局只有一层 tablist，三个标签都有明确对应的 tabpanel。
- 旧 Markdown 仍可读，结构化详情优先；脚本和危险链接不执行。
- Escape / 关闭按钮关闭弹窗，焦点回到触发入口。
- 手机详情铺满视口，页面不横向溢出；宽表格在自己的容器内滚动。
- 下载完整 JSON 保留白板与所有成果字段。

## 8. 后续优先级

1. **先补业务闭环**：真实文档打开地址、成果与子任务的关联、验证依据；这些决定用户能否使用成果。
2. **再补事件入口**：聊天交付卡片、已交付/待处理数量，以及跨会话回看成果的列表。
3. **按需求补协作操作**：验收、要求修改、再次执行。需要后端能力、权限、幂等和错误反馈一起设计。
4. **最后扩展历史体验**：真正的版本快照与差异比较。当前 versions 是描述列表，不应伪装为可恢复的版本库。

本轮已完成前端阅读结构、状态呈现、正式入口、视觉收敛及兼容修复。以上后续项目依赖明确的业务数据或后端动作，不以静态按钮模拟完成。
