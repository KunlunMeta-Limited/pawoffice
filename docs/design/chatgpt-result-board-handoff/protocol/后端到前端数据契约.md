# 后端 → 前端：成果数据契约

> 本文是「成果阅读页」相关数据的**协议层规定**汇总，来源为仓库权威定义：
> `integration/docs/office-integration.md`、`docs/architecture/result-deliveries.md`、
> `packages/protocol/src/office-integration.ts`、`packages/protocol/src/office-ui.ts`、`packages/protocol/src/dashboard.ts`。
> 字段以源码 Schema 为准，本文用于理解与设计评审，不是新增规范。
>
> 配套真实样例：`../sample/result-ready-round3.json`（ready）、`verified`、`rejected`、`draft-round1`（空态）、`whiteboard-*.json`（完整白板）。

---

## 1. 全景：数据怎么从后端走到页面

```text
业务后端 ──POST /api/pawoffice/messages──▶ PawOffice 服务端 ──SSE──▶ 浏览器页面
   │                                              │
   │◀──────────── 同一次 HTTP 请求的响应 ──────────┘
   │
   └─ 请求体 = 完整快照：{ schemaVersion, seq, workspace, conversations[] }
                                                  └─ conversation.whiteboard (task-board-v1)
                                                       ├─ steps / detailSections / summary
                                                       ├─ result      (result-v1)  ← 成果本身
                                                       └─ deliveries[]            ← 历史交付目录
```

三条关键性质：

1. **推送即全量**：每次都发该办公室的完整快照，后端不发送增量补丁。
2. **服务端只做校验与缓存**：最新的完整快照存在内存里，浏览器上线/重连时补发。服务端不存文件、不建版本仓库。
3. **前端只读消费**：PawOffice 负责展示、预览、下载；真实文件与历史版本由业务后端保管。

## 2. 传输层规则

### 2.1 地址与认证

```http
POST <PawOffice 服务地址>/api/pawoffice/messages
Authorization: Bearer <PAWOFFICE_API_KEY>
Content-Type: application/json
```

- 开发环境默认密钥是公开演示值 `pawoffice-demo-key`；公网必须换成私有值。
- 鉴权失败：`401`。密钥只在 HTTP 头里，不会下发给浏览器，也不会带到文件服务。

### 2.2 请求体

- 单个 JSON 对象，用 `type` 区分操作，其余字段是该操作的参数。
- **单次请求体上限 64 KiB**（`maxRelayMessageBytes = 65536`）。这是硬上限，成果内容要克制。
- 任何层级**禁止 `null`**。可选字段可以省略，省略即使用默认值。

### 2.3 响应信封

```json
{ "code": 200, "msg": "OK", "data": { } }
```

| 字段 | 说明 |
| --- | --- |
| `code` | 与 HTTP 状态码一致 |
| `msg` | 供人阅读的说明，程序判断应看 `code` 与 `data` |
| `data` | 该操作的结果；失败时为 `{ reasonCode, details, issues }` |

### 2.4 与成果相关的操作类型

| `type` | 用途 | 返回时机 |
| --- | --- | --- |
| `offices.initialize` | 初始化/更新办公室，携带完整快照 | 浏览器确认后 `200`；仅缓存未确认 `202` |
| `office.snapshot` | 更新某办公室完整状态 | 已应用 `200/applied`；已缓存 `202/cached`；旧版本 `200/ignored` |
| `office.read` | 查询目录或指定办公室状态 | 立即返回 |
| `office.capabilities` | 取 JSON Schema、人物、能力 | 立即返回，初始化前也可调用 |

> `202` 的准确含义：**最新状态已缓存，但本次请求没有拿到浏览器的应用确认**。它可能是页面离线，也可能是等待确认的请求容量已满。`202` 不能当作"页面已展示"。

### 2.5 HTTP 状态与错误

| 状态 | 含义 |
| --- | --- |
| `200` | 成功；结合 `data.status` 判断 applied / cached / ignored |
| `202` | 已缓存，未取得浏览器确认 |
| `400` | 请求格式、字段、ID 引用或操作方式无效（看 `reasonCode` 与 `issues`） |
| `401` / `403` | 密钥无效 / 拒绝访问 |
| `404` | 办公室不存在（`OFFICE_NOT_INITIALIZED`） |
| `408` | 等待浏览器或用户超时 |
| `409` | 版本/菜单冲突，或无在线接收者；含 `RESULT_HISTORY_CONFLICT`、`SEQ_CONFLICT`、`STALE_SEQ` 等 |
| `413` | 补齐默认值后超出大小限制 |
| `422` | 浏览器处理业务数据失败 |
| `503` | 队列/缓存/连接达到上限 |

## 3. 通用数据规则（最容易踩的）

1. **严格对象校验（strictObject）**：只接受 Schema 声明的字段。**多一个字段、拼错字段名、未知枚举值，整份快照直接 `400`，不会"尽量渲染"半成品。**
2. **默认值自动补齐**：可选文本默认 `""`、列表默认 `[]`、布尔默认 `false`、未知进度与资源指标默认 `-1`。
3. **ID 规则**：
   - 办公室、场景人物、命令、交互 ID：1–100 字符，只允许英文字母、数字、`_`、`.`、`:`、`-`。
   - 业务成员 ID、任务 ID：1–100 字符的非空字符串。
4. **时间**：必须是带时区的 ISO 8601（如 `2026-10-18T10:00:00Z`）。成果里的 `producedAt` / `updatedAt` / `createdAt` 使用后端给的时间，浏览器只按查看者时区格式化，不会用本地当前时间补造。
5. **URL**：只接受空串或完整 HTTP(S) 绝对地址；不传文件路径、相对路径、`data:` URI。
6. **禁止表现层数据**：不接受 HTML、CSS、内联样式、`style` 对象、像素值、`className`。图标、颜色、间距、版式全部由前端决定。
7. **嵌套上限**：JSON 最多 64 层，禁止 `__proto__`。

## 4. 快照结构（三层）

### 4.1 顶层：`officeSnapshot`

| 字段 | 类型 | 限制 | 说明 |
| --- | --- | --- | --- |
| `schemaVersion` | 字符串 | 固定 `"1.0"` | 协议版本 |
| `seq` | 整数 | 1–9007199254740991 | 每个办公室独立递增，用于乱序到达时取最新 |
| `workspace` | 对象 | `{ id, name }`，name ≤80 | `workspace.id` 即其他操作的 `teamId` |
| `conversations` | 数组 | ≤100 | 会话列表 |
| `system` | 对象 | 可选 | CPU/内存/网络，未知填 `-1` |

校验：`conversations[].id` 必须唯一。

### 4.2 会话：`conversation`

| 字段 | 类型 | 限制 | 说明 |
| --- | --- | --- | --- |
| `id` | 字符串 | ≤100 | 会话 ID |
| `title` | 字符串 | ≤160 | 显示名 |
| `employees` | 数组 | ≤200 | 业务成员；`sceneActorId` 绑定场景人物，多人可绑同一人物 |
| `tasks` | 数组 | ≤1000 | 任务：`id`/`title`(≤160)/`assigneeId`/`status`/`progress`/`updatedAt`/`summary`(≤1000) |
| `events` | 数组 | ≤500 | 动态：`kind` 为 note / task.assigned / task.started / task.blocked / task.completed |
| `whiteboard` | 对象 | 默认空白板 | **成果挂在白板下**：`whiteboard.result` |

校验：成员 ID 唯一；任务 ID 唯一；`assigneeId` 必须能在 `employees` 里找到。

### 4.3 任务状态枚举（`tasks[].status`）

`queued` / `running` / `blocked` / `completed` / `failed`

`progress` 为 `-1`（未知）或 0–100。

| 字段 | 类型 | 限制 | 说明 |
| --- | --- | --- | --- |
| `template` | 字符串 | 固定 `"task-board-v1"` | 模板标识 |
| `title` | 字符串 | ≤160 | 空串表示清空白板 |
| `status` | 枚举 | 见下 | **任务执行状态**，不是成果状态 |
| `tagline` | 字符串 | ≤40 | 标签行 |
| `description` | 字符串 | ≤300 | 原始目标 |
| `summary` | 字符串 | ≤300 | 墙上收起白板的概览；空时回退 `description` |
| `note` | 字符串 | ≤160 | 便签 |
| `detailSections` | 数组 | ≤8 | 结构化任务详情（原语 block 组合，见 7.3） |
| `detail` | 字符串 | ≤16000 | **已废弃**，仅旧快照兼容，前端不再渲染其 Markdown |
| `link` | 对象 | `label` ≤40、`url` | 可选外链 |
| `steps` | 数组 | ≤3 | 阶段：`id`/`title`(≤160)/`progress`(0–100 或 -1)/`state`(done/active/pending) |
| `result` | 对象 | — | **本轮成果**，`result-v1`，见第 6 节 |
| `deliveries` | 数组 | ≤20 | **历史交付目录**，见第 8 节 |

`whiteboard.status` 枚举：`queued` / `running` / `blocked` / `completed` / `failed`

> 白板与成果共用快照的 `seq`，必须随完整快照提交。省略 `whiteboard` 或传 `{}` 时使用默认空板；如果只想更新其他业务数据而要保留白板，必须在完整快照里带上当前白板内容。

## 6. 成果 `whiteboard.result`（`result-v1`）——核心

### 6.1 字段全表

| 字段 | 类型 | 上限/默认 | 语义 |
| --- | --- | --- | --- |
| `template` | 字符串 | 固定 `"result-v1"` | 模板 |
| `runId` | 字符串 | 可选 | 若填写，必须等于所属交付记录的 `id` |
| `title` | 字符串 | ≤160，默认 `""` | 成果标题 |
| `status` | 枚举 | 默认 `draft` | `draft` / `ready` / `verified` / `rejected` |
| `summary` | 字符串 | ≤300，默认 `""` | 首屏结论（一句话交代） |
| `verdict` | 字符串 | ≤300，默认 `""` | 验收结论 |
| `owner` | 字符串 | ≤40 | 负责人 |
| `team` / `teamSize` | 字符串 / 整数 | ≤40 / 0–99 | 团队名与人数（人数可省略，省略则不显示人数） |
| `producedAt` | 字符串 | ≤40 | 产出时间 |
| `updatedAt` | 字符串 | ≤40 | 更新时间（与产出时间分开显示） |
| `metrics` | 数组 | ≤12 | 指标，见 6.3 |
| `metricsTitle` / `metricsCaption` | 字符串 | ≤40 / ≤60 | 指标区标题与说明 |
| `artifacts` | 数组 | ≤8 | 交付文件，见 6.4 |
| `sections` | 数组 | ≤8 | 结构化交付区块，见第 7 节 |
| `checks` | 数组 | ≤12 | 验收清单，见 6.5 |
| `decisions` | 数组 | ≤8 | 过程决策：`id`/`question`/`choice`/`at` |
| `tasks` | 数组 | ≤12 | 任务明细：`id`/`title`≤80/`owner`≤40/`status`(todo·doing·blocked·done)/`progress`/`note`≤80 |
| `versions` | 数组 | ≤8 | 版本记录：`id`/`version`≤24/`note`≤120/`at`≤24/`author`≤40/`status`(draft·released·rolled-back) |
| `risks` | 数组 | ≤8 | 风险：`id`/`title`≤100/`level`(high·medium·low)/`status`(open·mitigating·closed)/`owner`≤40/`note`≤160 |
| `next` | 字符串数组 | ≤8，每条 ≤160 | 下一步行动 |
| `note` | 字符串 | ≤300 | 免责声明或补充说明 |

### 6.2 两个状态不要混

| 状态 | 来源 | 含义 |
| --- | --- | --- |
| 任务执行状态 | `whiteboard.status` | 任务做到哪一步：queued/running/blocked/completed/failed |
| 成果交付状态 | `result.status` | 成果可信到什么程度：draft/ready/verified/rejected |

**协议明确规定：任务完成不自动意味着成果验证通过。** 真实数据里 `ready` 可以配 `running`，只有 `verified` 才配 `completed`。

前端据此推导出 10 种展示态（`resultPresentation`），后端不需要额外提供：

`draft`（草稿）、`ready`（已交付）、`verified`（已验证）、`rejected`（未通过）、`conflict`（验证待核对：标了已验证但检查项有失败/待补充/失效）、`producing`（正在产出）、`blocked`（产出受阻）、`failed`（尚无成果）、`missing`（尚未交付）、`empty`（暂无成果）。

### 6.3 指标 `metrics[]`

| 字段 | 说明 |
| --- | --- |
| `id` / `label` / `value` / `unit` | 标识与展示字符串 |
| `kind` | `auto`(默认) / `comparison` / `value` / `status` / `target` / `text` |
| `emphasis` | `normal`(默认) / `primary`，用于突出首屏指标，不改变顺序 |
| `previous` / `change` / `trend` / `tone` | 前后对比：`trend` 为 up/down/flat，`tone` 为 positive/negative/neutral |
| `target` / `targetStatus` / `progress` | 目标型指标：`targetStatus` 为 met/missed/at-risk，`progress` 0–100 |

布局规则由前端按数量决定（0 项不显示、1 项整行、2 项两列、3 项三列、4 项 2×2、5–6 项三列，窄屏两列）。**后端不传布局。**

### 6.4 交付文件 `artifacts[]`

| 字段 | 说明 |
| --- | --- |
| `id` | 跨版本稳定标识 |
| `kind` | `document` / `image` / `link` / `data` |
| `title` / `description` | 展示标题与说明 |
| `content` | Markdown 正文，**≤8000 字符**；与 `url` 同时提供时优先非空 `content` |
| `url` | 可选完整 HTTP(S) 地址，指向该版本正文 |
| `versionId` | **不可变正文标识**；更新必须生成新值（历史交付里的 artifact 必填） |
| `version` | 仅供阅读的版本名（如 `v2.0`），不能替代 `versionId` |
| `runId` / `producedAt` / `mimeType` / `sha256` | 来源交付、产出时间、MIME、小写 64 位哈希（提供则预览与下载先校验） |
| `change` | added / updated / removed / unchanged，用于表达本轮变化 |

**两层标识**：`id` 稳定、`versionId` 标识正文。只改 `version` 文本不算新版本。

### 6.5 验收清单 `checks[]`

| 字段 | 说明 |
| --- | --- |
| `id` / `label` | 标识与文案（label ≤120） |
| `status` | `passed` / `pending` / `failed` |
| `artifactId` + `versionId` | 可选：把检查项绑定到具体产物版本 |

**失效规则（协议规定，前端实现）**：检查项绑定 `prd-v1`，而当前产物已更新为 `prd-v2` 时，该检查自动显示为"待补充"，要求重新验证。未绑定版本的旧检查，前端无法判断是否失效。

### 6.6 Schema 级联校验（发数据前必须满足）

1. 每个带 `artifactId` 的 section，必须能在本结果 `artifacts` 中找到**唯一且 `versionId` 一致**的产物，否则整份 `400`。
2. `artifactId` 与 `versionId` 必须**同时出现或同时不出现**。
3. `kind: "changes"` 的 section **不能**带 `purpose`。
4. `kind: "tests"` 的 section，`purpose` 只能是 `evidence`。
5. 交付记录中 `result` 与 `snapshotUrl` **二选一**，不能都给也不能都不给。
6. 交付记录的 `result.runId` 若填写，必须等于该记录 `id`。
7. 历史交付里的每个 artifact **必须有 `versionId`**。
8. 同一快照内，相同 `(id, versionId)` 的正文、MIME、哈希（无哈希时 URL）必须一致。

## 7. 结构化区块 `sections[]`（≤8 项）

`sections` 是带 `kind` 判别字段的数组。**所有 section 按数组顺序单列流式渲染**，`span`/`column` 仅为兼容旧数据保留，当前不影响布局。

### 7.1 七种固定 kind

| `kind` | 语义 | 主要字段与上限 |
| --- | --- | --- |
| `gallery` | 页面原型/预览 | `items` 1–8：`title`≤40、`meta`≤40、`status`(done·active·pending)、`image`（空串或 HTTP(S)） |
| `documents` | 产品文档 | `items` 1–8：`title`≤80、`version`≤24、`at`≤24、`status` 同上；可带 `artifactId`/`versionId` |
| `tests` | 测试与验收 | `metrics`≤4；`progress` 0–100；`progressLabel`≤40；`checks`≤12 |
| `api` | 接口交付 | `rows` 1–12：`endpoint`≤80、`method`(GET/POST/PUT/PATCH/DELETE 大写)、`status`、`at`≤24 |
| `environments` | 部署与发布 | `items` 1–8：`name`≤40、`status`(running·pending·stopped·failed)、`version`≤24、`at`≤24 |
| `files` | 文件与附件 | `items` 1–12：`name`≤80、`kind`(image·document·report·archive·other)、`size`≤16、`url` |
| `changes` | 本轮文件变更 | `files` 1–24：`path` 1–200（相对路径）、`status`(added·modified·deleted·renamed)、`added`/`deleted` 行数、`diff`（单文件 unified diff，≤16000）、`diffTruncated` |

### 7.2 共用字段

`kind`、`id`（1–100，字符集受限）、`title`（≤40）、`caption`（≤60，默认空串）、`emphasis`（normal/primary）、`purpose`（analysis / evidence / artifact-preview，用于语义归位）、`span`/`column`（兼容字段）。

### 7.3 第八种：`custom` + 原语 block

`custom` 用一组通用原语组合出版式：`layout` 为 `stack`/`columns`/`grid`/`cards`，`blocks` 1–24 项。

| `type` | 必填 | 上限要点 |
| --- | --- | --- |
| `heading` | `text` | text 1–80；`level` 为 h2/h3/h4 |
| `text` | `text`(Markdown) | ≤4000；忽略原始 HTML |
| `keyValue` | `items` | 1–8，label≤40、value≤160、`tone` |
| `stats` | `items` | 1–4，label≤20、value≤16、unit≤8 |
| `table` | `columns`、`rows` | columns 1–6、rows 1–12，单元格字符串≤300；`format` 为 text/number/percent/date/code/status/method/owner/link |
| `list` | `items` | 1–12，text 1–200，`status` 可空或 passed/pending/failed |
| `progress` | `value` | 0–100 |
| `chart` | `series` | 1–8，`chart` 为 bar/line/pie |
| `image` | — | `url` 空串或 HTTP(S)，空则占位框 |
| `diagram` | `source` | Mermaid 源文本 1–8000；**不能传 HTML/SVG** |
| `callout` | `text` | text 1–300；`tone` 为 info/success/warning/danger |
| `divider` | — | 分隔线 |

每个 block 都是严格对象：未知 `type`、拼错字段、非法枚举都会让**整份快照 `400`**。

## 8. 历史交付 `deliveries[]`（≤20 条）

| 字段 | 说明 |
| --- | --- |
| `id` | 唯一交付 ID |
| `sequence` | 唯一正整数，排序依据 |
| `turnId` | 可选：显式关联聊天轮次，不按到达顺序猜测 |
| `title` / `createdAt` | 标题（≤100）/ 创建时间（必填） |
| `board` | 可选：该次的任务状态、步骤、任务详情 |
| `result` **或** `snapshotUrl` | 二选一。内联成果，或指向外部 JSON 的完整 HTTP(S) 地址 |
| `snapshotUrl` 的要求 | 返回的是**单条交付对象**（不是整个办公室快照），不能再跳转；`id`/`sequence`/`turnId` 必须与请求一致；单份 ≤64 KiB |

数据职责划分：

- `whiteboard.result` = **当前有效集合**。更新文档后，未改且仍有效的继续出现；删除的产物必须从此列表移除。**前端不会从历史自动合并或恢复产物。**
- `deliveries` = **不可变交付目录**。每条表达"那次交付的内容"，可以只含当次新增/修改的文件；没有文件时可只记总结。
- 前端打开文件时按需拉取外部交付 JSON（最多 4 个并发、15 秒超时），失败只影响该文件，不回退到当前文件。
- 覆盖已知版本正文或已交付记录（含任务状态、摘要、详情、交付地址）会返回 `409 RESULT_HISTORY_CONFLICT`。
- 服务端只做缓存范围内的冲突检查，**不是持久化版本仓库**；强内容校验请填 `sha256`。

---

## 9. `seq` 与恢复顺序（每个办公室独立）

| 收到的版本 | 服务端处理 |
| --- | --- |
| 大于当前 `seq` | 应用完整快照 |
| 小于当前 `seq` | 保留当前状态，返回 `ignored` / `STALE_SEQ` |
| 等于当前 `seq` 且补齐默认值后内容相同 | 重新同步；确认后 `200/applied`，未确认 `202/cached` |
| 等于当前 `seq` 但内容不同 | `409 SEQ_CONFLICT` |

- 新快照的 `seq` 必须比此前大；后端重启后也要保持版本连续。
- 服务端重启会清空内存缓存，后端需要**重新初始化**；收到 `404 OFFICE_NOT_INITIALIZED` 时应补发完整初始化数据。
- 缓存上限：最多 100 个办公室、合计 8 MiB。
- 等待超时/连接中断**不代表状态回滚**，可用相同 `seq` + 相同内容重试；内容变了就必须增大 `seq`。

## 12. 机器可读 Schema

不确定字段时，让后端先取机器定义，不要靠文档记忆：

```json
{ "type": "office.capabilities" }
```

响应 `data` 包含：

| 字段 | 内容 |
| --- | --- |
| `ui.whiteboardSchema` | `whiteboard` 的完整 JSON Schema（含 `result`、`sections`、原语） |
| `ui.presentationSchema` / `ui.actionSchema` | 展示与用户操作的 Schema |
| `requests` / `responses` | 业务请求、成功/失败响应的 Schema |
| `scene` | 人物 ID、物品、行为参数 |

Schema 由同一份协议定义生成（`z.toJSONSchema(...)`），与运行时校验完全一致。发布前用它校验实际要发送的 `whiteboard.result`，比对照文档更可靠。

### 12.1 已导出的 Schema 文件

本目录 `schemas/` 下是直接从协议包生成的 JSON Schema（未手写）：

| 文件 | 对应 | 用途 |
| --- | --- | --- |
| `office-result.schema.json` | `officeResultSchema` | 只校验成果本身（`whiteboard.result`） |
| `whiteboard.schema.json` | `whiteboardTaskBoardSchema` | 白板 + 成果 + 历史交付 |
| `office-snapshot.schema.json` | `officeSnapshotSchema` | 整个办公室快照（`offices.initialize` / `office.snapshot` 请求体） |

生成方式（在仓库根目录执行）：

```bash
node --input-type=module -e "
import { z } from 'zod'
import { officeResultSchema } from '@pawoffice/protocol/office-ui'
process.stdout.write(JSON.stringify(z.toJSONSchema(officeResultSchema, { io: 'input' }), null, 2))
"
```

注意：`io: 'input'` 表示"可提交的输入"——带默认值的字段可以省略；`io: 'output'` 则会补齐默认字段，用于校验实际返回的数据。

### 12.2 后端自检示例

```js
import Ajv from 'ajv'
import schema from './schemas/office-result.schema.json' with { type: 'json' }

const validate = new Ajv({ strict: false }).compile(schema)
if (!validate(payload.whiteboard.result)) {
  console.error(validate.errors)   // 线上会变成整份快照 400，不会渲染半成品
}
```
