# AI Office / OpenPaw 设计与实现

更新日期：2026-09-20

本文是架构、协议、数据流和实现取舍的统一入口。原 `AI-Office-OpenPaw-总体架构与协议.md`、`architecture.md`、`b-line-design.md` 仅保留迁移页。2026-09-17 的真实 DeepSeek 复测、基线收敛和发布边界以本文及 `04-验收记录.md` 为准。该真实证据使用 OpenPaw 的 OpenAI-compatible Provider 适配器连接 DeepSeek 端点，不应把适配器标识误读为 `deepseek` Provider。

## 1. 总体架构

```text
Browser / React :5173
  -> officeGatewayApi
  -> Action Gateway :8765
       -> OpenCode v1 子集 HTTP -> openpaw-engine-host :4096
            -> Session/Turn Scheduler
            -> AgentLoop -> ToolHost / Approval -> Provider
            -> OPENPAW_HOME/sessions/*.jsonl
       -> /office/* 受控摘要
       -> /actions v1 尽力动画 -> Pixi/Spine
```

依赖方向固定为 `AI Office -> Gateway -> engine-host -> OpenPaw Engine/Core -> Provider`。React 不直接访问磁盘，Gateway 不写 session JSONL，Host 不依赖 React 或 OpenWork。会话事实与视觉投影严格分离。

图源：[系统上下文](./diagrams/01-system-context.drawio)、[Windows 部署](./diagrams/02-windows-deployment.drawio)、[对话时序](./diagrams/03-conversation-sequence.drawio)、[回合状态机](./diagrams/04-turn-state-machine.drawio)、[恢复流程](./diagrams/05-persistence-recovery.drawio)。这些文件是 diagrams.net XML，可供 Visio 导入；本轮只校验 XML 结构，未完成 Visio Desktop 实机验收，也未生成原生 VSDX。

## 2. 进程与端口

| 进程 | 通用默认 | Windows native | 职责 |
| --- | --- | --- | --- |
| React/Vite | 5173 | `127.0.0.1:5173` | UI、会话视图、场景 |
| Action Gateway | 8765 | `127.0.0.1:8765` | Office API、Host 代理、摘要和动作队列 |
| engine-host | 端口 0 | `127.0.0.1:4096` | OpenCode v1 子集、调度、审批、Provider、JSONL |

通用 Host 的端口 0 用于动态分配；native 脚本显式固定 4096，不冲突。当前运行态 4096、8765、5173 均仅监听 `127.0.0.1` 且健康检查为 200。自动化使用随机端口，不复用或停止用户服务。

## 3. OpenPaw 独立运行

`openpaw-engine-host` 和 CLI 的 `engine-host` feature 均为 optional，默认 feature 关闭。默认 CLI、no-default、sidecar 和 Host feature 模式均已构建/测试；默认依赖树不含 `axum` 或 `openpaw-engine-host`。因此 AI Office 通过 Host 转发和隔离的理解正确：OpenPaw 可以独立运行，AI Office 只是外部客户端。

本轮进一步收敛了独立运行边界：Tokio `signal` feature 只在 engine-host 依赖启用；`.env` 只在 `chat`、`--engine-host` 和 `config show` 模型入口加载，无效模型配置不会阻断 `hello/session/tool/init` 等独立命令；Provider HTTP 客户端恢复默认协议协商，不再全局强制 HTTP/1.1；AgentLoop 恢复原有 10-200ms 快速退避，同时 503/529、rate-limit 和 overload 仍最多重试一次。

## 4. HTTP 与旧协议兼容

旧 README 的 `/actions` 仅是办公室动画协议，合法的 `desk_visit`、`desk_visit_tour`、`set_state` 和 `POST/GET /actions` 继续兼容。当前实现增加字段校验、批次原子性和 Origin 白名单；非法输入范围收紧是有意行为。

对话不再通过 `/actions`。React 调用 Gateway 的 `/office/conversations*`，Gateway 转发到 Host 的 OpenCode v1 子集。相比把动画队列当业务总线，这种连接方式更合理：

1. Host 是会话唯一写入者，历史和终态可恢复。
2. 不同 session 可并行，同 session 线性化。
3. Provider、工具、审批、动画失败彼此隔离。
4. Gateway 统一进行脱敏、缓存、错误映射和浏览器安全边界。

异步 202/204 只加快接收确认，不能保证完整回复更快；总耗时仍取决于 Provider、工具、审批、网络、持久化和渲染。

Host 核心路由包括 `/global/health`、`/session`、`/session/:id/message`、`/session/:id/turns`、`/session/:id/prompt_async`、`/session/:id/abort`、`/session/status`、SSE、Provider 和 permission。成功监听的 stdout 机器协议保持：

```text
opencode server listening on http://127.0.0.1:<port>
```

### 4.1 T3 会话创建收敛

`POST /session` 的工作区来源固定为 `x-opencode-directory` 请求头、`directory` 查询参数、CLI 默认工作区，优先级严格按该顺序。JSON body 中的 `directory` 不再属于协议；AI Office Gateway 已改为只通过请求头传递工作区，避免同一参数存在三种来源并产生漂移。

会话创建现在先完成 Provider、工作区、工具注册表和 `AgentLoop` 构造，全部成功后才创建 JSONL 并写入 Meta/Metadata；两条初始记录任一写入失败都会关闭 writer 并删除不完整文件，只有持久化成功的 handle 才进入 session 表。因此配置错误返回 400 时，不会再出现磁盘有 JSONL、`GET /session` 仍可见的幽灵会话。

本轮保留两个有意的文件位置偏差：`HostConfig` 仍定义在 host 本地 `protocol.rs`，`run()` 仍实现在 `http.rs`，由 `lib.rs` 统一 re-export。对外 API 与 T3 要求一致，且类型没有移入 `openpaw-core`/`openpaw-engine`；仅为满足文件名而搬移会扩大差异、打乱 HTTP/config 职责边界，没有运行时、兼容性或性能收益。`protocol.rs` 也暂不拆分，因为当前 serde 快照、HTTP DTO 和 HostConfig 仍属于同一兼容边界，拆分不会改善协议稳定性。

## 5. 对话提交、并发与幂等

```text
UI generation + stable requestID
  -> Gateway 按 sessionId/requestID 合并并缓存确认 30 秒
  -> Host admission / idempotency / active-turn check
  -> OpenPaw-Turn-ID 响应头
  -> Gateway 202 {accepted, sessionId, turnID}
  -> Controller 绑定 turnID/userMessageID/generation
  -> status + turns + messages 对账唯一终态
```

Gateway 的消息提交缓存同时处理“并发重复请求”和“确认响应丢失后重试”。相同 session/requestID 且正文相同返回同一 promise 或短期完成确认；正文不同返回 `idempotency_conflict`。Controller 只在 `active_turn` 或旧 Host 没有 code 的 409 时接管活动回合，不会把幂等冲突错误绑定到别的 turn。

Host 同一 session 最多一个 queued/running turn；不同 session 进入全局 FIFO，默认 4 running、32 queued。接收、用户消息和终态使用持久化事务语义，失败和取消以 system 正文保留。

幂等重放的判定顺序是一个稳定性边界：Host 先根据 session 已持久化的 `requestID` 记录和无副作用的 provider/model 标识计算指纹，再构造 Provider。已验证的“同一运行时 Provider 凭据失效”场景中，已接收请求仍能返回原 `turnID`；正常 Provider 的 Host 重启 replay 也有独立回归覆盖。当前尚未把“Host 重启后同时修改 Provider 凭据或地址”的组合场景作为已通过证据。`accept_turn` 内仍保留同一 `turn_gate` 下的最终幂等检查，防止并发请求绕过线性化边界。

## 6. 第二轮失败根因与修复

原问题不是“AI Office 不允许第二轮”，而是 Provider 过载与错误映射叠加：

- 一个逻辑回合曾执行初始调用加三次重试，短时间最多四次上游请求。
- 兼容端点可能 HTTP 200，但 SSE 正文内返回 overload/error frame。
- Host 把 overload、rate limit、server、protocol 等错误过度归类为 `provider_rate_limited`。
- Gateway/Controller 缺少稳定 turnID 和错误 code，重试或 409 时可能接管错误回合。

当前修复：

- 明确 503/529、overload 和 rate-limit 最多重试一次，即最多两次上游调用；判断不依赖服务端正文必须包含 overload 关键词，其他网络瞬态故障保留原有受控策略。
- OpenAI-compatible HTTP 200 SSE 内嵌错误会解析 `status/code/type/retry_after/retry_after_secs`，兼容数字或字符串形式的 `retry_after`；429、503、529 均结构化失败且不得生成 `Final`。
- 稳定区分 `provider_rate_limited`、`provider_overloaded`、`provider_server_error`、`provider_timeout`、`provider_protocol_error`。
- Host 409 返回 `active_turn`；Gateway 透传 `code/retryable` 和 `OpenPaw-Turn-ID`。
- 组件回归验证第一轮成功、第二轮 overload 仅两次上游调用、第三轮恢复成功；真实三端另验证同一 session 第一、第二、第三轮连续完成。
- 真实 Provider 三轮受控烟测结果为：第一轮准确报告 protocol error，第二、三轮完成；不再误报所有失败为“请求过于频繁”。

## 7. 持久化与恢复

事实优先级为 `JSONL turn/message -> Host REST -> Gateway 短缓存 -> Browser cache -> animation`。Host 使用接收、prepare、commit 和 outcome 记录保证未 commit 生成内容不可见、已 commit 内容和终态可恢复。启动扫描把 hanging turn 闭合为 `failed/host_restarted`，二次扫描幂等。

三端测试已覆盖 Host 重启后失败正文、Gateway 重启后历史保持、浏览器切页与刷新恢复、入场前失败正文恢复。失败和取消不是页面底部瞬时状态，而是目标对话的一部分。

Host 受控关闭会先停止 admission、取消活动 session，再等待任务注册表收敛；若进入强制终止路径，收割结果仍以“注册表最终是否清空”为准，不能因为执行过 abort 就无条件报告关闭失败。若截止时间后仍有任务残留，HTTP 层才返回关闭失败；已清空的强制收割路径保持成功返回并由下一次启动恢复持久事实。

## 8. 长文本与 SSE

OpenAI/Anthropic 流处理使用增量字节解码，严格校验 UTF-8、JSON、工具参数和正式终止证据。随机 HTTP chunk、中文、emoji、截断和 2 MiB 边界均有契约测试。最新完整回合由前端 Store 按回合保留，不因后置 marker 被拆散淘汰。

三端系统旅程验证 3850 UTF-16 code units 的中文/emoji 文本完整保留；LLM 契约另外覆盖长流随机分块。

## 9. 动画与任务

### 9.1 v1.5 当前实现

Host 将 turn 开始、匹配工具、审批和结束映射为 `set_state`/`desk_visit`。每个 turn 按工具首次出现顺序为李研、周理、陈书各最多发送一次 visit，同角色后续工具只更新状态；前端按 FIFO 串行播放，并延迟应用会中断当前 mission 的最终状态。空闲时不产生默认工作动画；角色 owner 隔离避免一个 session 的结束把另一个 session 仍在使用的角色置空闲。Office POST 超时或失败不影响回合结果。

Gateway 同时维护有界内存 cursor journal 和旧客户端兼容队列。新前端使用 `GET /actions?after=<cursor>` 增量读取并检测内存缺口；旧无 cursor 客户端仍使用读取后清空的兼容队列。该机制提高单进程内的恢复能力，但 journal 不落盘、没有消费者 ACK，也不能跨 Gateway 重启恢复。

任务中心的创建、取消和重试是 T11 之后增加的受控写入扩展：只原子写入 `<OPENPAW_HOME>/goals/*.md` 元数据，并通过 Host 创建/取消会话；Gateway 不直接写入或删除 session JSONL。原 T11 的五个 GET 摘要接口本身仍保持只读。

办公室工作区只接受 `OPENPAW_OFFICE_WORKSPACE`。未配置或只含空白时 Gateway 不得使用自身启动目录：文件列表返回空数组，工作区摘要返回空 root，文件正文接口返回 503 配置错误。任务或普通对话未提供工作区时不发送 `x-opencode-directory`，由 Host 使用 CLI 默认工作区；Gateway 不替 Host 推断 cwd。

### 9.2 v1.5 限制

当前 `/actions` 没有持久 outbox/journal、消费者 ACK、完整 `sessionId/turnID/eventID/sequence` 因果信封和 snapshot。cursor 只能在单次 Gateway 进程生命周期内重放；兼容队列与 cursor journal 并存时，`/health.queued` 也不能代表某个 cursor 消费者的真实待处理量。因此它满足原 master-plan 的尽力动画，但不能证明多浏览器、多会话、重启下的可靠因果动画。

### 9.3 v2 目标

可靠动画需要 Host outbox、Gateway journal、事件信封、单调 sequence、消费者 lease、ACK/cursor、gap 和 snapshot。每个 session 保存逻辑投影，只有选中 session 驱动物理 Canvas。该方案目前只有 CHG 设计，尚未实施，必须单独作为发布阻断记录。

## 10. 安全与性能边界

- Gateway 仅绑定回环，Host URL 必须是无凭据/path/query/fragment 的 HTTP(S) origin。
- 文件和技能读取限制在配置根，拒绝 `..`、符号链接和过大正文。
- 浏览器消息只返回元数据和 text 白名单，不返回 reasoning 或工具敏感输入输出。
- 日志不得记录 API key、完整 Prompt 或 Provider 原始敏感正文。
- 会话列表使用摘要缓存，正文按当前选择和活动变化加载；不能为了切换速度在首页启动时全量加载所有历史正文。

## 12. 当前结论

核心分层、Host 隔离、跨 session 并行、第二轮恢复、失败持久化、幂等重放、受控关闭、Windows 端口合同、Provider 故障分类、投影隔离和 4/32 容量边界已有分开的自动化、三端和真实 DeepSeek 证据支持；其中 DeepSeek 200/200、mock 故障矩阵、投影隔离和容量边界不是同一次运行。该证据不覆盖历史失败矩阵、20 session x 50 turn 混合压力、破坏性重启、可靠动画 v2、OpenWork T7/T9、冻结提交、人工发布审批以及 Visio Desktop 实机验收，这些仍阻断完整发布。本轮没有修改 UI 布局、字体或 Canvas。
